# TransMove update — 11 October 2026

## Branding and app delivery

The supplied TransMove logo is now the brand reference. The original supplied image is preserved as `assets/images/logo.jpg`; transparent wordmark and square app-icon variants are included for practical display sizes.

- Navy `#082f5b`, blue `#125fbe`, and orange `#ff6b08` replace the previous green brand palette. Payment success/error colours retain their meaning.
- The home page, navigation, buttons, admin tabs, charts, public policies, and dark theme share the new styling. Responsive spacing and clearer active navigation improve readability.
- Web/PWA icons, favicon, Android launcher/adaptive icons, iOS icon, and native splash screens are updated. The service-worker cache version changes to deliver the new assets.
- Android version 1.1, build 2 compiled successfully. `downloads/transmove-android.apk` contains the updated app. It is a debug-signed installation package, not a Play Store release.
- Web assets were packaged and synchronized into both Android and iOS projects. A native iOS archive/IPA cannot be compiled or signed on this Windows machine; that step requires macOS/Xcode and Apple signing. The iPhone browser/PWA uses the updated website.

## Portal and advertising fixes

- The sidebar always has a visible way to reopen it. Header and sidebar controls update their accessible state correctly; mobile navigation closes appropriately when switching to desktop.
- Admin tabs use consistent grid alignment and preserve whole words. Header actions and table controls wrap appropriately instead of overlapping.
- Drivers and machinery owners can open advertising through their navigation. The campaign form now uses the existing modal API correctly.
- General advertising campaigns persist in the shared database rather than relying on server-local drafts. A linked payment record preserves campaign information and allows admin review after a server restart.
- Machinery advertising requests appear in the admin advertising queue from their durable payment records, including older requests with retained payment metadata.
- The queue distinguishes content review from payment review and exposes payment proofs. Campaigns publish only after the required approvals; durations start when publication is approved.
- Repeated payment references, incorrect amounts, inactive payment destinations, invalid proofs, unauthorized ownership, and invalid links are rejected. Failed machinery publication restores a pending payment so it can be retried.
- Pending renewals and rejected renewal payments preserve an already-running machinery promotion. Direct publication without payment approval is blocked.
- Approved campaigns render in their intended dashboard slots and expire on schedule. Impression/click calls are connected to the backend.
- City targeting and featured upgrades were disabled because the promised delivery features were not implemented. Users cannot purchase these unavailable upgrades.
- Admin analytics counting now accommodates the driver-presence table's primary key. The connection indicator checks the current cloud backend instead of calling the obsolete Appwrite account function.
- Admin analytics, advertising, and payments refresh periodically while visible, without replacing an open review dialog.

## Known limits and recovery

Old campaigns that existed only in an earlier server's local storage cannot be recovered after that storage is lost. Retained legacy drafts are identified as needing resubmission. Durable machinery payment records remain reviewable.

This was a focused regression pass on the reported flows and shared layout, not proof that every possible account, screen, or external integration is bug-free. Production database schema/permissions and storage availability still determine whether authenticated operations succeed.
